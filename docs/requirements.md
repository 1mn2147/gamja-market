# 감자마켓 제품 요구사항

## 1. 문서 정보

- 제품명: Tiny Second-hand Shopping Platform 감자마켓
- 문서 상태: 초안
- 목적: 초기 기능 목록을 구현 및 검증 가능한 제품 요구사항으로 구체화한다.
- 우선순위: `P0`은 최초 출시 필수, `P1`은 출시 후 개선 항목이다.
- 결제 연동: 토스페이먼츠 SDK v2 결제위젯 또는 토스페이먼츠 호스팅
  결제창을 사용한다.
- 준거 기준: PCI DSS v4.0.1, OWASP API Security Top 10:2023,
  ISO/IEC 25010:2023, ISO/IEC 27001:2022 및 적용 가능한 ISMS-P 기준

## 2. 제품 목표

감자마켓은 사용자가 가까운 지역의 중고 상품을 등록하고 탐색하며, 판매자와
대화하고, 직거래에 연결된 에스크로 결제와 정산을 안전하게 수행할 수 있는
소규모 중고거래 플랫폼이다. 플랫폼은 신고, 차단, 관리자 조치를 통해 악성
사용자와 상품의 노출 및 활동을 통제해야 한다.

## 3. 핵심 원칙

1. 모든 데이터 접근은 인증 여부와 객체 소유권을 서버에서 검증한다.
2. 거래는 구매자와 판매자가 직접 만나 상품을 인도하는 직거래로 제한한다.
3. 송금은 임의의 사용자 간 자유 송금이 아니라 상품 거래에 연결된 에스크로
   결제와 판매대금 정산으로 처리한다.
4. 카드번호, 유효기간, CVC/CVV와 같은 카드 계정 데이터는 토스페이먼츠가
   제공하는 결제 UI에서만 입력하며 감자마켓 클라이언트, 서버, 로그, 분석
   도구를 거치거나 저장하지 않는다.
5. 결제, 환불, 정산 기록은 삭제하거나 덮어쓰지 않고 불변 원장으로 남긴다.
6. 관리자는 업무에 필요한 범위만 조회하고 모든 관리 행위를 감사 로그로
   남긴다.
7. 숨김, 정지, 차단 상태는 화면뿐 아니라 API에서도 동일하게 강제한다.

## 4. 범위

### 4.1 포함 범위

- 회원가입, 인증, 로그인, 회원 상태 관리
- 상품 등록, 조회, 수정, 삭제 및 판매 상태 관리
- 키워드 검색, 필터, 정렬, 페이지네이션
- 상품 기반 1:1 채팅
- 직거래 요청, 토스페이먼츠 에스크로 결제, 상품 인도, 구매 확정, 정산,
  취소 및 환불
- 사용자, 상품, 메시지 신고와 사용자 차단
- 관리자용 사용자, 상품, 신고, 거래 및 결제 관리
- 보안 이벤트와 관리자 행위 감사

### 4.2 제외 범위

- 상품과 무관한 사용자 간 자유 송금
- 자체 카드 입력 화면, 카드번호 결제 API 및 카드 계정 데이터의 직접 처리
- 배송 거래 및 플랫폼 자체 배송·물류 운영
- 경매, 공동구매, 구독, 다중 통화
- 공개 커뮤니티 게시판과 소셜 피드
- 개인화 추천과 광고 시스템
- 세분화된 관리자 역할 체계

## 5. 사용자 역할

| 역할 | 설명 | 주요 권한 |
| --- | --- | --- |
| 비회원 | 로그인하지 않은 방문자 | 공개 상품 조회 및 검색 |
| 회원 | 인증을 완료한 일반 사용자 | 상품 등록, 채팅, 거래, 신고, 차단 |
| 제한 회원 | 정지 또는 일부 기능이 제한된 사용자 | 정책에 따라 읽기만 허용하거나 접근 차단 |
| 최고관리자 | 지정된 1인의 플랫폼 운영 담당자 | 사용자, 상품, 신고, 거래 관리 |
| 토스페이먼츠 | 외부 결제 및 지급대행 주체 | 결제 승인, 취소, 환불, 지급 상태 제공 |

## 6. 상태 모델

### 6.1 사용자 상태

`인증대기 -> 활성 -> 이용정지 -> 활성`

`인증대기 | 활성 | 이용정지 -> 탈퇴`

- `인증대기`: 인증 완료 전 상태이며 거래 기능을 사용할 수 없다.
- `활성`: 일반 기능을 사용할 수 있다.
- `이용정지`: 상품 등록, 채팅, 신규 거래가 금지된다.
- `탈퇴`: 로그인할 수 없으며 개인정보는 보존 정책에 따라 처리한다.

### 6.2 상품 상태

`임시저장 -> 판매중 -> 예약중 -> 판매완료`

`판매중 | 예약중 -> 숨김 | 삭제`

- 거래가 취소되면 다른 활성 거래가 없는 경우 `예약중` 상품을 `판매중`으로
  되돌릴 수 있다.
- 일반 사용자는 `숨김` 또는 `삭제` 상품을 조회할 수 없다.

### 6.3 거래 상태

`요청 -> 판매자수락 -> 결제완료(에스크로 보관) -> 인도완료 -> 구매확정 -> 정산대기 -> 정산완료`

예외 상태는 `거절`, `취소`, `환불`, `분쟁`, `결제실패`, `정산실패`다.

- 허용된 상태 전이만 수행할 수 있다.
- 거래 상태와 결제 상태는 분리해 기록하되 서로 모순되지 않아야 한다.
- 판매자의 인도 완료 처리 후 구매자가 7일 동안 구매확정이나 분쟁 신청을
  하지 않으면 거래를 자동으로 구매확정 처리한다.
- 구매확정 또는 자동확정 시점부터 7일 동안 판매대금 정산을 보류한다.

### 6.4 신고 상태

`접수 -> 검토중 -> 조치완료 | 기각`

## 7. 기능 요구사항

### 7.1 회원 및 인증

| ID | 우선순위 | 요구사항 |
| --- | --- | --- |
| AUTH-001 | P0 | 사용자는 중복되지 않는 이메일 또는 휴대전화로 가입할 수 있어야 한다. |
| AUTH-002 | P0 | 사용자는 소유 확인을 위한 인증 절차를 완료해야 활성 상태가 된다. |
| AUTH-003 | P0 | 활성 사용자는 로그인과 로그아웃을 할 수 있어야 한다. |
| AUTH-004 | P0 | 사용자는 검증된 연락처를 이용해 비밀번호를 재설정할 수 있어야 한다. |
| AUTH-005 | P0 | 사용자는 회원 탈퇴를 요청할 수 있어야 하며 처리 결과를 확인할 수 있어야 한다. |
| AUTH-006 | P0 | 정지 또는 탈퇴 사용자는 로그인하거나 신규 쓰기 작업을 수행할 수 없어야 한다. |
| AUTH-007 | P0 | 로그인 실패 횟수와 인증 요청 빈도를 제한해야 한다. |
| AUTH-008 | P0 | 미성년자는 가입할 수 없어야 하며 가입 과정에서 성인 여부를 검증해야 한다. |
| AUTH-009 | P1 | 사용자는 활성 로그인 세션을 확인하고 개별 세션을 종료할 수 있어야 한다. |

검증 기준:

- 동일한 식별자로 두 개의 활성 계정을 생성할 수 없다.
- 성인 여부를 확인할 수 없거나 미성년자로 확인된 사용자의 가입은 완료되지 않는다.
- 비밀번호 원문은 저장하거나 로그에 남기지 않는다.
- 인증되지 않은 요청으로 다른 사용자의 개인정보를 조회하거나 수정할 수 없다.

### 7.2 상품 관리

| ID | 우선순위 | 요구사항 |
| --- | --- | --- |
| ITEM-001 | P0 | 활성 회원은 제목, 설명, 가격, 카테고리, 거래 지역, 이미지를 입력해 상품을 등록할 수 있어야 한다. |
| ITEM-002 | P0 | 작성자만 자신의 상품을 수정하거나 삭제할 수 있어야 한다. |
| ITEM-003 | P0 | 사용자는 접근 가능한 상품의 상세 정보와 판매 상태를 조회할 수 있어야 한다. |
| ITEM-004 | P0 | 가격은 0 이상의 정수 금액이어야 하며 서버에서 검증해야 한다. |
| ITEM-005 | P0 | 업로드 이미지의 확장자, 실제 형식, 크기, 개수를 제한해야 한다. |
| ITEM-006 | P0 | 결제가 진행 중인 상품의 가격과 핵심 거래 조건을 임의로 변경할 수 없어야 한다. |
| ITEM-007 | P0 | 숨김, 삭제 또는 판매완료 상품에는 신규 거래 요청을 생성할 수 없어야 한다. |
| ITEM-008 | P1 | 작성자는 상품을 임시저장한 뒤 게시할 수 있어야 한다. |
| ITEM-009 | P0 | 상품의 거래 지역은 행정동 단위로만 등록하고 일반 사용자에게 상세 주소를 공개하지 않아야 한다. |

검증 기준:

- 다른 사용자의 상품 ID를 사용한 수정 및 삭제 요청은 거부된다.
- 스크립트가 포함된 제목이나 설명은 실행되지 않는다.
- 허용되지 않은 파일을 이미지로 위장해 업로드할 수 없다.

### 7.3 검색과 탐색

| ID | 우선순위 | 요구사항 |
| --- | --- | --- |
| SEARCH-001 | P0 | 사용자는 상품 제목과 설명을 키워드로 검색할 수 있어야 한다. |
| SEARCH-002 | P0 | 카테고리, 가격 범위, 지역, 판매 상태로 결과를 필터링할 수 있어야 한다. |
| SEARCH-003 | P0 | 최신순, 낮은 가격순, 높은 가격순으로 정렬할 수 있어야 한다. |
| SEARCH-004 | P0 | 검색 결과는 페이지네이션되어야 하며 안정적인 정렬 순서를 유지해야 한다. |
| SEARCH-005 | P0 | 사용자가 선택하거나 확인한 행정동과 플랫폼이 인접 지역으로 정의한 가까운 행정동의 상품만 노출해야 한다. |
| SEARCH-006 | P0 | 상품 목록과 상세 화면에는 행정동 정보만 표시하고 정확한 주소나 좌표를 노출하지 않아야 한다. |
| SEARCH-007 | P1 | 최근 검색어와 검색 조건을 사용자 단위로 저장할 수 있어야 한다. |

검증 기준:

- 빈 검색어, 특수문자, 최대 길이 입력도 서버 오류를 발생시키지 않는다.
- 숨김 또는 삭제 처리된 상품은 기존 검색 결과에서도 다시 노출되지 않는다.
- 인접 지역이 아닌 행정동의 상품은 검색 조건을 변조해도 조회되지 않는다.

### 7.4 채팅

| ID | 우선순위 | 요구사항 |
| --- | --- | --- |
| CHAT-001 | P0 | 활성 회원은 상품을 기준으로 판매자와 1:1 대화를 시작할 수 있어야 한다. |
| CHAT-002 | P0 | 대화 참여자만 대화방과 메시지를 조회할 수 있어야 한다. |
| CHAT-003 | P0 | 참여자는 텍스트 메시지를 전송하고 최근 메시지와 읽지 않은 메시지 수를 확인할 수 있어야 한다. |
| CHAT-004 | P0 | 차단 관계이거나 이용정지 상태인 사용자는 신규 메시지를 전송할 수 없어야 한다. |
| CHAT-005 | P0 | 메시지 길이와 전송 빈도를 제한하고 위험한 콘텐츠를 안전하게 처리해야 한다. |
| CHAT-006 | P1 | 사용자는 새 메시지 알림을 켜거나 끌 수 있어야 한다. |

검증 기준:

- 대화방 ID를 추측해도 비참여자는 메시지를 조회할 수 없다.
- 차단 직후부터 API와 실시간 연결 모두에서 신규 메시지가 거부된다.
- 메시지 내용에 포함된 HTML 또는 스크립트가 실행되지 않는다.

### 7.5 거래, 결제 및 정산

| ID | 우선순위 | 요구사항 |
| --- | --- | --- |
| PAY-001 | P0 | 구매자는 판매중인 상품에 대해 거래 요청을 생성할 수 있어야 한다. |
| PAY-002 | P0 | 판매자는 자신의 상품에 대한 거래 요청을 수락하거나 거절할 수 있어야 한다. |
| PAY-003 | P0 | 판매자 수락 시점의 상품 가격과 거래 조건을 거래 기록에 고정해야 한다. |
| PAY-004 | P0 | 구매자는 수락된 거래에 대해 토스페이먼츠 SDK v2 결제위젯 또는 토스페이먼츠 호스팅 결제창으로 에스크로 결제를 할 수 있어야 한다. |

| PAY-007 | P0 | 판매자의 인도 완료 처리 후 7일 동안 구매자가 구매확정 또는 분쟁 신청을 하지 않으면 자동으로 구매확정해야 한다. |
| PAY-008 | P0 | 구매확정 또는 자동확정 시점부터 7일 동안 에스크로 판매대금의 정산을 보류한 뒤 판매자에게 정산해야 한다. |

| PAY-010 | P0 | 금액 변동은 불변 원장에 사유와 연관 거래를 포함해 기록해야 한다. |
| PAY-011 | P0 | 결제 실패, 콜백 중복, 타임아웃 이후에도 거래와 상품 상태가 일관되어야 한다. |

### 8.2 데이터 일관성과 신뢰성

- 상품 예약과 결제 성공 처리는 원자적으로 연결하거나 보상 절차를 제공한다.
- 에스크로 보관, 구매확정, 정산대기, 환불, 정산완료 전이는 원장 기록과
  일관되어야 한다.
- 외부 결제 콜백은 서명, 출처, 금액, 거래 식별자를 검증한다.
- 외부 시스템 타임아웃은 성공 또는 실패로 즉시 단정하지 않고 조회 또는
  재처리 가능한 상태로 기록한다.
- 토스페이먼츠 장애율과 타임아웃이 임계치를 넘으면 서킷 브레이커를 열어 신규
  결제 시도를 일시 차단하고 사용자에게 결제 시스템 점검 상태를 안내한다.
- 서킷 브레이커는 제한된 시험 호출로 복구 여부를 확인한 뒤 정상 상태로
  전환하며, 미확정 거래는 정기 대사 작업으로 복구한다.
- 자동 재시도는 멱등성이 보장된 요청에만 지수 백오프와 무작위 지연을 적용한다.
- 중요 데이터 변경에는 생성자와 변경 시각을 기록한다.
- 백업 및 복구 절차는 사용자, 상품, 거래, 원장, 감사 로그를 포함한다.

### 8.3 성능

- 일반 상품 조회와 검색 API는 정상 부하에서 95백분위 응답 시간 1초 이내를
  목표로 한다. 토스페이먼츠 API 대기 시간은 별도로 측정한다.
- 목록 API는 한 번에 반환할 최대 개수를 제한한다.
- 이미지 원본 크기를 제한하고 서비스용 크기로 변환해 제공한다.

### 8.4 접근성과 사용성

- 핵심 가입, 상품 등록, 검색, 채팅, 결제 흐름은 키보드로 조작할 수 있어야 한다.
- 입력 오류는 문제가 발생한 필드와 해결 방법을 식별할 수 있게 표시한다.
- 색상만으로 거래 상태나 오류 상태를 전달하지 않는다.
- 결제, 환불, 차단, 탈퇴 등 중요한 작업은 결과와 영향을 명확히 안내한다.

### 8.5 개인정보와 보존

- 기능 수행에 필요한 최소한의 개인정보만 수집한다.
- 직거래 서비스이므로 배송 주소를 수집하거나 저장하지 않는다.
- 위치 확인에 정확한 좌표를 사용하더라도 행정동 변환 후 원본 좌표를 일반
  사용자에게 공개하지 않는다.
- 애플리케이션 역할, 최고관리자, 결제 처리 서비스 계정, 데이터베이스 운영
  계정을 분리하고 역할 기반 접근통제와 최소 권한을 적용한다.
- 최고관리자 1인 체계라도 최고관리자 애플리케이션 권한과 데이터베이스 직접
  접근 권한을 동일하게 부여하지 않는다.
- 개인정보의 수집 목적, 보존 기간, 삭제 또는 분리 보관 기준을 명시한다.
- 로그에는 비밀번호, 인증 코드, 전체 결제수단, 세션 토큰을 기록하지 않는다.
- 탈퇴 후에도 법적 또는 분쟁 대응상 필요한 거래 기록은 개인정보와 분리해
  정책에 따른 기간 동안 보존한다.

### 8.6 표준 준수 및 관리체계

#### PCI DSS v4.0.1

- 토스페이먼츠가 제공하는 결제위젯 또는 호스팅 결제창의 결제 입력 요소만
  사용하고 모든 카드 계정 데이터 기능을 PCI DSS 준수 결제대행사에 위탁한다.
- 감자마켓은 PCI DSS SAQ A 적격 환경을 목표로 하며, 운영 전 계약된 매입사,
  결제대행사 또는 적격 심사 주체를 통해 실제 적격성과 검증 제출 방식을
  확인한다. 외부 위탁만으로 PCI DSS 책임이 완전히 면제된 것으로 간주하지 않는다.
- 토스페이먼츠의 PCI DSS 준수 증빙과 제공 서비스 범위를 정기적으로 확인하고
  공급자 변경 또는 결제 흐름 변경 시 PCI 범위를 다시 평가한다.
- 결제 페이지 스크립트 공격에 취약하지 않음을 입증할 수 있도록 배포 승인,
  CSP 위반 보고, 파일·스크립트 변경 탐지 및 정기 취약점 점검 증적을 보존한다.

#### OWASP API Security Top 10:2023

- 공개 API와 관리자 API의 전체 목록, 소유자, 버전, 인증 방식, 데이터 등급을
  관리하고 폐기된 API와 디버그 엔드포인트를 외부에 노출하지 않는다.
- 결제 승인, 환불, 신고, 채팅, 가입과 같은 민감 업무 흐름에 요청 제한,
  자동화 탐지, 객체 소유권 및 상태 전이 검증을 적용한다.
- 토스페이먼츠 응답과 웹훅을 신뢰된 내부 입력으로 간주하지 않고 스키마,
  허용값, 크기, 금액 및 연관 주문을 검증한다.

#### ISO/IEC 25010:2023

- 결제 통합의 기능 적합성, 성능 효율성, 호환성, 상호작용성, 신뢰성, 보안성,
  유지보수성, 유연성 및 안전성에 대한 측정 가능한 인수 기준을 관리한다.
- 토스페이먼츠 장애, 지연, 중복 응답, 순서 역전 웹훅, 부분 실패를 결함 허용과
  복구성 시험에 포함한다.
- 외부 API 버전, 스키마 및 동작 변경을 호환성 시험으로 탐지하고 배포 전에
  테스트 환경에서 승인, 취소, 환불, 웹훅, 대사 흐름을 검증한다.

#### ISO/IEC 27001:2022 및 ISMS-P

- 정보자산, 개인정보, 결제 식별정보, 비밀 키, 공급자 연동을 자산 목록에
  등록하고 소유자, 위험, 보호조치 및 잔여 위험을 정기적으로 검토한다.
- 접근통제, 암호화, 개발 보안, 공급자 관리, 로그·모니터링, 사고 대응,
  백업·복구 및 개인정보 생명주기에 대한 정책과 운영 증적을 유지한다.
- 개인정보와 결제 식별정보의 수집, 이용, 제공, 보존 및 파기는 적용 가능한
  국내 법령과 ISMS-P 기준에 따라 검토하며, 법적 적용 여부는 출시 전 전문
  검토를 통해 확정한다.
- 보안 사고 발생 시 키 폐기, 토스페이먼츠 통보, 영향 범위 조사, 법정 통지,
  복구 및 재발 방지 절차를 실행할 수 있어야 한다.

## 9. 핵심 인수 시나리오

1. 신규 사용자가 인증을 완료하고 로그인한 뒤 상품을 등록할 수 있다.
2. 비회원이 공개 상품을 검색하고 필터와 페이지 이동을 사용할 수 있다.
3. 다른 사용자가 상품 판매자와 대화를 시작하고 메시지를 교환할 수 있다.
4. 차단 이후 상대 사용자의 기존 대화와 상품이 숨겨지고 신규 메시지와 거래
   요청이 모두 거부된다.
5. 판매자가 거래 요청을 수락하고 구매자가 한 번만 결제할 수 있다.
6. 동시에 두 구매자가 결제를 요청해도 상품은 한 명에게만 예약된다.
7. 에스크로 결제대금은 구매확정 또는 7일 자동확정 후에도 7일 동안 정산되지
   않으며, 보류 기간 종료 후 정산 내역과 불변 원장 기록이 생성된다.
8. 구매확정 후 7일 이내의 환불 요청을 처리해도 원결제와 환불 기록이 모두
   보존된다.
9. 신고된 상품을 최고관리자가 숨기면 상세 조회와 검색에서 즉시 제외된다.
10. 최고관리자 조치의 대상, 사유, 변경 전후 값이 감사 로그에서 확인된다.
11. 회원과 최고관리자 모두 권한이 없는 객체 ID로 다른 사용자의 정보를 조회할
    수 없다.
12. 악성 입력, 위장 이미지, 중복 결제 콜백이 데이터 손상 없이 거부된다.
13. 카드 정보를 입력해도 카드 계정 데이터가 감자마켓 네트워크 요청, 서버,
    로그, 분석 도구 및 백업에서 발견되지 않는다.
14. 변조된 성공 URL이나 일반 결제 웹훅을 전송해도 토스페이먼츠 결제 조회
    결과와 주문번호·금액·상태가 일치하지 않으면 결제가 완료되지 않는다.
15. 동일한 결제 승인, 취소 또는 환불 요청을 반복해도 한 번만 처리된다.
16. 토스페이먼츠 장애 시 서킷 브레이커가 신규 호출을 제한하고 비결제 기능은
    정상 동작하며, 미확정 거래는 복구 후 대사된다.
17. TLS 1.0과 TLS 1.1 연결은 거부되고 TLS 1.2 또는 TLS 1.3 연결만 성공한다.
18. `payout.changed` 또는 `seller.changed` 웹훅의 서명이 없거나 올바르지 않으면
    지급 및 판매자 상태를 변경하지 않는다.

## 10. 승인된 정책 결정

아래 정책 결정은 2026-07-15에 승인되었으며, 구현과 테스트의 기준으로 사용한다.

1. 토스페이먼츠 연동은 sandbox와 테스트 UI까지만 구현한다. 실결제·실정산, MID, 지급대행 및 판매자 본인확인 연동은 이번 범위에서 제외한다.
2. 분쟁 최종 처리는 지정된 최고관리자 1인이 수행하며, 증빙 보존 기간은 탈퇴 사용자 관련 데이터와 동일하게 탈퇴 후 1년으로 한다.
3. 고위험 관리자 작업에는 별도 승인자를 두지 않는다. 지정된 최고관리자 1인의 재인증, 사유 입력 및 감사 로그를 필수로 한다.
4. 로그는 생성 후 2년 보관한다. 개인정보·채팅·거래 데이터는 탈퇴 후 1년까지 보관한다. 감사 로그를 포함한 로그는 생성 후 2년 보관한다.

## 11. 출시 완료 기준

- 모든 `P0` 요구사항에 대응하는 구현과 자동화된 테스트가 존재한다.
- 인증 우회, 객체 소유권 우회, 관리자 권한 우회 테스트가 통과한다.
- 중복 결제, 동시 구매, 환불 및 정산 실패 시나리오가 검증된다.
- PCI DSS SAQ A 적격성과 검증 제출 방식을 계약된 결제 관계자와 확인하고,
  요구되는 자가진단과 증적을 완료한다.
- 카드 계정 데이터 비보유 검증, TLS 구성 검사, 결제 페이지 스크립트 변경
  탐지 및 비밀 키 유출 검사가 통과한다.
- OWASP API Security Top 10:2023 위협 모델과 보안 테스트가 완료된다.
- 토스페이먼츠 장애, 서킷 브레이커, 웹훅 재전송·위조·순서 역전 및 거래 대사
  시험이 통과한다.
- ISO/IEC 27001 기반 위험 목록, 자산 목록, 접근권한 검토, 공급자 검토,
  사고 대응 및 복구 증적이 준비되어 있다.
- 주요 가입, 상품 등록, 검색, 채팅, 거래, 신고, 관리자 흐름을 종단 간으로
  검증한다.
- 알려진 심각도 높음 이상의 보안 취약점이 남아 있지 않다.
- 승인된 결제 범위, 분쟁 권한, 고위험 작업 통제 및 보존 정책이 구현·테스트·운영 문서와 일치한다.
