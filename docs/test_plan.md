# 감자마켓 테스트 전략 및 명세

## 1. 문서 정보

- 목적: 감자마켓의 기능, 결제 무결성, 보안, 품질 및 화면 요구사항을 반복
  실행 가능한 테스트로 검증한다.
- 기준 문서: [제품 요구사항](./requirements.md), [페이지 구성 설계](./page_desc.md),
  [Codex 활용 개발 WBS](./wbs.md), [기술 스택 및 개발 계획](./tech_stack.md)
- 적용 범위: 요구사항 88개, 페이지 29개, 공통 컴포넌트와 시스템 상태
- 최우선 위험: 객체 권한 우회, 중복 결제·정산, 결제 결과 위조, 카드 데이터
  유입, 차단·제재 우회, 시간 경계 오류

## 2. 테스트 목표

1. P0 기능이 정상·실패·권한·경계·동시성 조건에서 요구사항대로 동작한다.
2. 거래, 결제, 환불, 정산 상태가 네트워크 장애와 재시도 후에도 일관된다.
3. 토스페이먼츠 데이터만 신뢰하지 않고 서버 주문과 조회 결과로 결제를 확정한다.
4. 카드 계정 데이터와 비밀값이 감자마켓의 모든 처리·관측 경로에서 배제된다.
5. 비회원, 인증대기, 활성, 이용정지, 차단, 최고관리자 권한이 모든 채널에서
   동일하게 강제된다.
6. 검색·일반 조회의 성능, WCAG 2.2 AA 접근성, 반응형 화면과 장애 복구 기준을
   충족한다.

## 3. 범위와 제외 범위

### 3.1 포함

- 단위, 컴포넌트, API, DB·큐·객체 저장소 통합, 계약, E2E 테스트
- 토스페이먼츠 샌드박스 결제·조회·취소·환불·웹훅·지급 상태 테스트
- 인증·인가, 입력 검증, 속도 제한, 파일 업로드, OWASP API 보안 테스트
- 경쟁 상태, 멱등성, 시간 경계, 장애 주입, 대사와 복구 테스트
- 29개 페이지의 권한·상태·반응형·접근성·콘텐츠 테스트
- PCI DSS SAQ A 적격성 증거와 ISO/IEC 25010·27001, ISMS-P 통제 증거 확인

### 3.2 제외 또는 조건부

- 토스페이먼츠 실계정 결제는 DEC-01과 별도 운영 승인 전 수행하지 않는다.
- 실제 카드번호, CVC/CVV, PIN, 전체 트랙 데이터는 어떤 환경에서도 테스트
  데이터로 만들거나 전송하지 않는다.
- 재인증된 최고관리자 1인의 분쟁 최종 조정은 사유·감사 로그·정산 중지 보존과 함께 검증한다.
- 개인정보·채팅·거래 데이터의 탈퇴 후 1년 보존과 로그 생성 후 2년 보존은 주입 가능한 서버 시계로 경계를 검증한다.
- P1 기능은 P0 출시 판정을 차단하지 않되 구현된 항목은 동일 기준으로 검증한다.

## 4. 테스트 계층과 자동화 비율

| 계층 | 대상 | 실행 시점 | 주요 책임 |
| --- | --- | --- | --- |
| 정적 검사 | 포맷, 타입, SAST, 의존성, 비밀, IaC | 모든 변경 | 빠른 차단 |
| 단위 | 검증기, 권한 정책, 상태 전이, 기한 계산, 원장 규칙 | 모든 변경 | 경계값과 결정 로직 |
| 컴포넌트 | 폼, 표, 타임라인, 결제 상태, 접근성 | 프런트엔드 변경 | UI 상태와 상호작용 |
| API 통합 | 인증, DB 제약, 검색, 업로드, 거래 명령 | 기능 변경 | 서버 권한과 영속성 |
| 계약 | OpenAPI, 이벤트, Toss 요청·응답·웹훅 | 계약 변경 | 공급자·소비자 호환성 |
| E2E | 핵심 사용자와 관리자 여정 | 병합 전·야간 | 실제 시스템 연결 |
| 비기능 | 성능, 보안, 복원력, 접근성, 호환성 | 마일스톤·출시 | 품질 게이트 |

단위·API 테스트로 상태 조합을 넓게 검증하고, E2E는 핵심 여정과 통합 실패에
집중한다. 시간 기반 테스트는 실제 7일 대기 대신 주입 가능한 서버 시계와 작업
스케줄러를 사용하되, 스테이징에서 실제 예약 작업 연결도 별도로 확인한다.

### 4.1 선택 도구

| 대상 | 도구 | 적용 범위 |
| --- | --- | --- |
| NestJS 단위·통합 | Jest, Supertest | 서비스, guard, REST API, raw-body 웹훅 |
| Next.js UI | Jest, Testing Library | Client Component, 폼, 상태, 접근성 의미 구조 |
| Next.js Server Component | Playwright | 비동기 렌더링과 실제 라우팅 중심 E2E |
| 데이터·큐 | Jest + Compose | PostgreSQL 18, Prisma migration, Redis 8, BullMQ |
| API·이벤트 계약 | OpenAPI diff, JSON Schema | `/api/v1`, outbox 이벤트, Toss 웹훅 fixture |
| 브라우저 E2E | Playwright | Chromium, Firefox, WebKit과 모바일 뷰포트 |
| 접근성 | axe-core, Playwright | WCAG 2.2 AA 자동 검사와 수동 체크 보조 |
| 성능 | k6 | 검색, 일반 GET, 채팅·웹훅 적체 시나리오 |
| 보안 | ESLint/SAST, SCA, 비밀·컨테이너 스캔 | 코드, lockfile, 이미지, IaC |
| 외부 결제 | 로컬 Toss stub + Toss sandbox | 결정적 실패 주입과 공급자 계약 검증 |

단위 테스트는 외부 시스템을 stub 처리하되, API 통합 테스트부터는 실제
PostgreSQL·Redis·BullMQ를 사용한다. Toss stub은 공식 응답·웹훅 fixture를
버전 관리하고 sandbox 테스트가 최종 공급자 계약을 확인한다.

| Toss 샌드박스 | 스테이징 앱, Toss SDK v2와 테스트 결제 키 | Toss 공식 테스트 수단 | 결제·웹훅·취소·환불 계약 |

분석 도구에도 카드·인증 코드·채팅 본문·신고 증빙을 보내지 않는다.

## 6. 테스트 데이터 설계

### 6.1 사용자

| 데이터 ID | 상태·관계 | 사용 목적 |
| --- | --- | --- |
| U-GUEST | 비회원 | 공개 조회와 로그인 유도 |
| U-PENDING | 인증대기 성인 미확인 | 쓰기 차단 |
| U-MINOR | 미성년 확인 결과 | 가입 거부 |
| U-BUYER-A | 활성, A동 | 구매·신고·차단 |
| U-BUYER-B | 활성, 인접 B동 | 동시 구매 경쟁 |
| U-SELLER | 활성, A동 | 상품·거래·정산 |
| U-REMOTE | 활성, 비인접 지역 | 지역 경계 차단 |
| U-SUSPENDED | 이용정지 | 로그인·쓰기·실시간 차단 |
| U-WITHDRAWN | 탈퇴 | 로그인 및 개인정보 접근 차단 |
| U-ADMIN | 지정된 최고관리자 1인 | 운영·감사·재인증 |

`U-BUYER-A -> U-SELLER` 차단과 차단 해제 상태를 각각 준비한다. 테스트는 매번
고유 식별자를 생성하며 연락처와 이름은 실제 사람의 정보를 사용하지 않는다.

### 6.2 상품과 거래

- 상품: 임시저장, 판매중, 예약중, 판매완료, 숨김, 삭제 상태를 각 1개 이상 둔다.
- 지역: 선택 행정동, 인접 행정동, 비인접 행정동을 명시적으로 구분한다.
- 거래: 요청, 판매자수락, 결제완료, 인도완료, 구매확정, 정산대기, 정산완료와
  거절, 취소, 환불, 분쟁, 결제실패, 정산실패를 준비한다.
- 결제: 유효, 중복, 미확정, 주문 불일치, 금액 불일치, 역순 웹훅을 준비한다.
- 시간: 각 7일 기한의 직전 1초, 정확한 경계, 직후 1초를 준비한다.

- 상품 목록은 각 구간의 4·3·2·1열 규칙을 따른다.
- 고정 행동, 필터, 표, 채팅 입력이 본문을 가리거나 화면 밖으로 잘리지 않는다.

- 로딩, 이미지 실패, 배지 변화로 레이아웃이 불필요하게 이동하지 않는다.
- 관리자 모바일에서도 기능이 삭제되지 않고 필수 조회·행동에 접근할 수 있다.

## 11. 성능, 복원력과 관측성

### 11.1 성능

소규모 웹사이트 기준으로 측정 환경을 먼저 마련한다. 정상 동시 사용자, 데이터 규모, 요청 비율의 수치가 확정되기 전에는 측정값을 참고치로만 사용하며 임의의 낮은 부하로 P95 통과를 선언하지 않는다.

| 테스트 ID | 대상 | 합격 기준 |
| --- | --- | --- |
| PERF-001 | 검색 API | 합의된 정상 부하에서 P95 1초 이하, 오류율 기준 이하 |
| PERF-002 | 일반 GET API | 합의된 정상 부하에서 P95 1초 이하 |
| PERF-003 | 이미지 목록·상세 | 대표 네트워크에서 레이아웃 이동과 과도한 전송 없음 |
| PERF-004 | 채팅 | 메시지 폭주 시 속도 제한, 다른 기능의 가용성 유지 |
| PERF-005 | 웹훅 | 내구 저장 후 10초 이내 응답, 비동기 적체 관측 가능 |

Toss 외부 지연은 내부 처리 시간과 분리해 기록한다. 외부 지연으로 전체 앱의
일반 탐색·채팅 기능이 실패하면 불합격이다.

### 11.3 관측성 판정

- 결제 승인, 웹훅 적체·실패, 대사 불일치, 환불·정산 실패에 경보가 발생한다.
- 로그의 요청 ID로 사용자 요청, 내부 명령, 외부 Toss 호출을 연결할 수 있다.
- 로그와 추적에는 비밀번호, 인증 코드, 카드 정보, 시크릿, 채팅 본문이 없다.
- 사용자 상태와 금액 상태를 로그에서 임의 수정하지 않고 불변 식별자로 추적한다.
- 경보에는 안전한 운영 절차와 담당자가 연결된다.

## 13. 진입·종료와 출시 판정

### 13.1 테스트 진입 조건

- 대상 요구사항, API 계약, UI 상태, 보류 정책 의존성이 식별되어 있다.
- 격리 가능한 테스트 데이터와 환경이 준비되어 있다.
- 마이그레이션과 롤백 또는 순방향 복구 절차가 검토되었다.
- Toss 테스트 키와 웹훅 대상은 비밀 관리 시스템으로 주입된다.
- 시간과 외부 장애를 제어할 테스트 훅이 운영 환경에서 비활성화됨을 보장한다.

### 13.2 작업 종료 조건

- 관련 P0 테스트가 모두 통과하고 요구사항 추적이 100%다.
- 새 코드의 핵심 분기와 실패 경로가 단위 또는 통합 테스트로 보호된다.
- 치명·높음 보안 결함과 차단 접근성 결함이 0건이다.
- 불안정 테스트가 없거나 승인된 격리·수정 기한이 있다.
- 실패 증거와 로그에서 민감정보 노출이 없다.

### 13.3 출시 차단 기준

다음 중 하나라도 해당하면 출시하지 않는다.

- 미구현 또는 미검증 P0 요구사항이 있다.
- 결제 중복, 금액 불일치, 원장 불변성, 정산 중지 테스트가 실패한다.
- 카드 계정 데이터가 감자마켓 경로에서 한 건이라도 발견된다.
- 인증·객체 권한·관리자 권한 우회가 가능하다.
- 위조 리다이렉트·웹훅으로 결제완료 상태를 만들 수 있다.
- 데이터 손실 또는 대사 불가능한 거래 상태가 존재한다.
- 치명·높음 보안 결함, 차단 접근성 결함, 미복구 마이그레이션 위험이 있다.
- 승인된 DEC-01~04의 범위·통제가 구현 또는 검증과 다르다.
- 배포 런타임·프레임워크 버전이 `tech_stack.md` 기준선 또는 lockfile과 다르다.

## 15. Codex 테스트 실행 절차

1. 변경 작업의 요구사항 ID와 페이지 ID를 읽고 영향 테스트를 선택한다.
2. 정상 경로보다 먼저 권한, 경계값, 중복, 실패, 시간 조건을 추가한다.
3. 가장 작은 단위 테스트를 실행하고 API 통합, 계약, E2E 순서로 확장한다.
4. 실패하면 구현을 수정한 뒤 동일 테스트와 인접 회귀를 다시 실행한다.
5. 결제·권한 변경은 독립 보안 검토와 경쟁 상태 테스트를 추가한다.
6. 화면 변경은 대표 뷰포트 스크린샷, 키보드, 자동 접근성 검사를 수행한다.
7. 완료 보고에 실행 명령, 통과·실패 개수, 미실행 항목, 잔여 위험을 기록한다.

`WBS-01.02`에서 루트 `package.json`에 다음 표준 명령을 구현한다. 패키지별
하위 명령은 달라도 되지만 CI와 완료 보고에서는 이 이름을 사용한다.

| 순서 | 명령 | 통과 기준 |
| ---: | --- | --- |
| 1 | `pnpm install --frozen-lockfile` | lockfile 변경 없이 설치 |
| 2 | `pnpm lint` | ESLint 오류 0건 |
| 3 | `pnpm typecheck` | 모든 workspace TypeScript 오류 0건 |
| 4 | `pnpm test:unit` | Jest 단위·컴포넌트 테스트 통과 |
| 5 | `pnpm test:integration` | PostgreSQL·Redis·BullMQ 통합 테스트 통과 |
| 6 | `pnpm test:contract` | OpenAPI·이벤트·Toss fixture 계약 차이 승인 |
| 7 | `pnpm test:e2e` | Playwright P0 핵심 여정 통과 |
| 8 | `pnpm test:a11y` | axe 차단 위반 0건 |
| 9 | `pnpm test:security` | 치명·높음 미조치 취약점과 비밀 유출 0건 |
| 10 | `pnpm test:release` | 빌드, 2~9번 검사와 기준선 통과; 성능·복구는 실행 명령 추가 후 포함 |

Next.js 16은 `next lint`를 제공하지 않으므로 `pnpm lint`는 ESLint CLI를 직접
호출한다. 명령이 구현되지 않았거나 실행되지 않은 검증은 통과로 표시할 수 없다.
CI와 새 환경에서는 위 명령 전에 PostgreSQL 18·Redis 8을 준비하고 Prisma client 생성과 migration deploy를 완료해야 한다. Playwright 명령 전에는 Chromium과 운영체제 의존성을 설치한다. `test:release`는 빌드와 2~9번 검사를 모두 실행하며, 성능·복구 게이트는 WBS-09~10에서 실행 가능한 명령이 추가되기 전까지 별도 미검증 항목으로 보고한다.


## 16. 추적성 완전성 검사

문서와 코드의 CI에는 다음 검사를 포함한다.

- `requirements.md`의 요구사항 ID가 유일하고 연속적인지 확인한다.
- `page_desc.md`의 29개 페이지 ID가 유일한지 확인한다.
- 모든 P0 요구사항이 하나 이상의 WBS 작업과 테스트 ID에 연결되는지 확인한다.
- 구현 완료 요구사항이 실패·보류 테스트에만 연결되지 않았는지 확인한다.
- 삭제되거나 이름이 바뀐 요구사항·페이지 ID가 코드와 테스트에 남지 않았는지
  확인한다.
- 보류 정책이 결정되면 결정 ID, 요구사항, 구현, 테스트가 함께 갱신되는지
  확인한다.
