# 결제 위협 모델

## 범위와 신뢰 경계

브라우저는 상품·거래 상태를 표시하고 Toss가 제공하는 결제 UI로 이동할 수
있지만, 금액·주문·결제 성공을 확정하지 않는다. API는 주문·거래·원장을 소유하고
Toss API 및 웹훅은 외부 신뢰 경계다. worker는 내구 저장된 이벤트만 처리한다.

카드번호, 유효기간, CVC/CVV, PIN, 전체 트랙 데이터는 Toss UI 외에 입력되지
않으며 웹, API, DB, Redis, 큐, 로그, 분석, 오류 추적, 백업에 저장·전송되지
않는다.

## 위협과 통제

| 위협 | 통제 | 검증 |
| --- | --- | --- |
| 리다이렉트의 `orderId`·`amount`·`paymentKey` 변조 | 서버 주문의 소유자·금액·주문번호 대조 후 서버에서 승인 | SEC-PAY-003, API-PAY-004 |
| 일반 결제 웹훅 위조 또는 본문 위조 | 본문으로 확정하지 않고 `paymentKey` 조회 결과를 대조 | CON-PAY-007, SEC-PAY-008 |
| 지급·판매자 웹훅 위조·재전송 | raw body·전송 시각으로 HMAC SHA-256 검증, 상수 시간 비교 | SEC-PAY-009, CON-PAY-010 |
| 중복 POST, 타임아웃 뒤 재시도 | 고유 Idempotency-Key와 최초 결과·내부 원장 보존 | CON-PAY-005, CON-PAY-006 |
| 동시 결제로 상품 이중 예약 | DB 제약·트랜잭션 잠금으로 하나의 성공만 허용 | API-TRADE-004 |
| Toss 장애·응답 유실 | 서킷 브레이커, `UNCONFIRMED` 기록, 조회 기반 대사 | RES-PAY-013, RES-PAY-014 |
| 카드·시크릿 유출 | 호스팅 결제 UI, 환경별 비밀 분리, 로그·분석 차단, CSP | COMP-PCI-001~005, SEC-PAY-012 |
| 웹훅 처리 지연·worker 중단 | 수신 사실을 내구 저장 후 10초 안에 응답, outbox·재시도 | PERF-PAY-011, RES-004 |

## 필수 설계 규칙

1. Toss POST마다 고유 `Idempotency-Key`와 최초 응답을 보관한다.
2. 웹훅 전송 ID와 이벤트 상태로 중복·역순 이벤트를 무해하게 처리한다.
3. 금액 변동은 거래 식별자와 사유가 있는 추가 전용 원장 이벤트다.
4. 결제·환불·정산 호출의 시크릿은 서버 비밀 관리 경계 밖으로 절대 내보내지 않는다.
5. DEC-01에 따라 결제는 Toss sandbox와 테스트 UI로만 검증한다. 실결제 MID,
   지급대행과 판매자 본인확인 연동은 포함하지 않는다.
